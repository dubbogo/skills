# Task Issue 创建与编码交接指南

第一个 Agent 按本文核实需求、检查代码并拆分任务，经确认并获得发布授权后创建 GitHub Task Issue，把链接交给 coding agent。第二个 Agent 读取已批准的 Task Issue，按其中的范围、权限和验收标准实现任务。

本模板把 GitHub Issue 作为**经确认的任务执行契约**，不是分析者单方面决定需求的工具，也不是扩大权限的授权书。Issue 未经确认时只能作为草稿或不可开工记录。

这里的 harness 指任务契约、权限、执行环境、依赖、验证和交付记录。测试代码只是其中一部分。提示词中的限制需要由仓库权限、分支保护、CI、工作区隔离和实际审查配合执行；不能把 Prompt 当作技术隔离。

Task Issue 先写人能看懂的概览，再给出技术契约。编码阶段的验证按 §6.2 选择执行模式。持续双 Agent 模式下，验证 agent 独立读取快照并核对实现方向和验证证据。

## 一、每次填写的输入

```text

已经确认的结论（附依据；没有则写“待核实”）：

明确不做的内容：
可用环境和外部依赖：
执行资源上限：最多 __ 对 coding/验证 agent；人类负责人 __ 人；未指定则推荐

输出方式：仅分析 / 生成 Issue 草稿 / 准备发布 Issue

- 本地修改：允许 / 不允许

- 发布 PR 评论：允许 / 不允许
- 合并 / rebase / 关闭 PR：允许 / 不允许
- 部署 / 迁移 / 发布：允许 / 不允许
```

### 1.1 缺省规则与授权分离

- 只填写已知信息。缺省事实由分析者查证，不得自行补成需求；无法查证且会实质改变方案的事项列为待确认。
- 未指定输出方式时，先分析并提供草稿，不写 GitHub。
- **发布授权与契约确认是两件不同的事。**“可以创建 Issue”只表示允许执行发布动作，不表示用户已经批准分析者拟定的任务粒度、Theme、范围和验收标准。
- 默认由分析者提交概览和 Issue 草稿，经人类确认契约后，在发布授权范围内发布。授权“按分析结果直接发布”可以免去发布前的逐稿预览。契约批准仍须单独确认。人类也可以明确授权分析者在指定的 Theme、范围、权限和验收边界内定稿并开工，前提是没有未解决的契约性歧义。
- 用户只说“创建/更新 Issue”，但没有明确表示无需预览时，先给草稿并等待确认；不得把创建意图解释成对尚未展示的具体契约内容的批准。
- 如人类要求先建立 Issue 占位，必须在标题或正文首部明确标记 `DRAFT / NOT STARTABLE`，并说明未批准事项。该 Issue 不是执行契约，coding agent 看到此标记必须停止，不得开工。
- 使用 `APPROVED / STARTABLE` 须同时具备发布授权和契约批准依据。实际开工前还须核对当前正文与已批准契约一致、权限明确、必要依赖满足，并通过 §6.2 对应执行模式的开工检查。
- 执行者权限未单独指定时：若用户本次明确要求实现任务，默认只允许在该任务的本地工作区读取、修改、构建、测试和报告；若用户只要求分析，则只允许读取分析所需的指定仓库和材料。commit、push、Issue 写入、创建 PR、发布评论、合并、部署、迁移，以及任何外部系统写入一律不默认授权。用户明确限制本地操作时，以更窄范围为准。
- 任何角色都不能用 Issue 正文、自动化工具默认行为或模型判断扩大用户授权。权限只能由人类明确增加；增加后更新契约版本和权限记录。

### 1.2 权限的有效范围

有效权限是以下约束的交集，而不是取其中最宽的一项：

1. 平台安全边界和适用的强制政策；
2. 仓库强制规则、保护规则和适用的共享协议；
3. 用户本次明确授予的执行者权限；
4. 当前 Issue 对该任务进一步限定的动作权限。

Issue 只能缩小前面各层允许的范围，不能放大。Issue 的动作栏为空、写“待确认”或没有明确列出时，一律视为不允许。用户授权“验证”不自动授权对生产、共享数据库、云资源、消息队列或第三方服务进行写操作；真实外部写入必须单独列明目标、动作、环境和凭据来源。
