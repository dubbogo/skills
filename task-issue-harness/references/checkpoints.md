## 六、检查点和人类可读输出

### 6.1 标准执行流程

1. 分析者核实需求和代码事实，产出概览、Theme、任务草稿和完整验收矩阵。
2. 按 §1.1 分别核对发布授权和契约批准，记录获批内容及固定版本。
3. 分析者在两项依据齐备时发布 `APPROVED / STARTABLE` Issue。经授权发布的未批准占位仍为 `DRAFT / NOT STARTABLE`。
4. Coding agent 将当前契约与原批准记录及固定版本核对，生成开工快照。
5. 按 §6.2 取得对应执行模式的开工放行，再进入实现阶段。
6. Coding agent 交付切片快照，按执行模式安排过程检查、记录方向和验证证据。
7. PASS 后按检查点继续；契约内缺陷 CORRECT；契约/权限/证据/环境问题 HOLD。
8. 最终交付时重新固定快照，按执行模式完成最终验证，并报告验证方式、Harness 状态和产品验收状态。

### 6.2 宿主能力与降级

持续双 Agent 模式要求宿主实际具备独立会话、快照传递、原始证据保存、验证反馈接收和继续/暂停控制。各模式共用第三节的契约批准检查和 Issue 的权限、依赖及验收要求。

| 执行模式 | 开工放行 | 最终结论 |
|---|---|---|
| 持续双 Agent（默认） | 验证 agent 独立核对开工快照和契约，实际反馈 `CONTINUE` | 按各检查点和最终快照报告独立验证结果 |
| `FINAL_INDEPENDENT_REVIEW` | Coding agent 完成开工自检后，由人类明确批准以此模式开工或恢复 | 独立验证者核对最终快照及证据，报告最终独立验证结果 |
| `SELF_CHECK_ONLY` | Coding agent 完成开工自检后，由人类明确批准以此模式开工或恢复 | 报告逐项自检结果，独立验证记为 `NOT_RUN` |

- 默认模式无法取得开工反馈时，进入 `BLOCKED / HOLD`。改用降级模式时，记录人类批准依据、适用契约版本和执行模式。按所选模式安排各阶段检查点，验证 agent 的 `CONTINUE` 仅用于实际独立检查后放行。
- 模式降级、重新启用双 Agent 或更换验证会话均需记录；影响快照或证据时重新验证。

### 6.3 检查点状态机

| 技术验证 | Theme / 范围 | 证据与权限 | 动作 | 后续 |
|---|---|---|---|---|
| 必需项均 PASS 或有依据的 N/A | 符合 | 快照匹配、无越权 | CONTINUE | 放行当前阶段 |
| FAIL | 符合 | 问题在已批准范围内 | CORRECT | 修复后重验受影响项 |
| PASS | 偏离 | 改动违反 Theme 或范围 | CORRECT 或 HOLD | 可在契约内纠偏则 CORRECT；需改契约则 HOLD |
| BLOCKED / NOT_RUN | 符合或未定 | 缺少本检查点必需的环境、依赖、验证或证据 | HOLD | 人类决定恢复方式 |
| 任意 | 任意 | 未授权外部写、生产凭据滥用、快照无法确认 | HOLD | 立即停止相关操作并报告 |
| 同一验收项连续两轮 CORRECT 仍失败 | 任意 | 纠偏未消除问题 | HOLD | 交人类决定，不得无限循环 |

`CONTINUE` 只代表当前检查点放行，不代表最终验收、可合并或允许发布。`CORRECT` 只处理契约内问题，不得借纠偏修改契约。`HOLD` 期间，两个 Agent 都不能自行修改 Issue；恢复必须由人类决定并由分析者更新契约。

### 6.4 人类可读检查点

```text
【任务检查点】
Issue / 契约版本：
snapshot_id / HEAD：
目标：一句话说明本任务带来的变化。
进展：已完成的可观察行为，以及未完成部分。
实际变化：修改模块、diff 位置、新增文件和依赖变化。
方向：符合 / 偏离 / 证据不足；附依据。
验证：PASS / FAIL / BLOCKED / NOT_RUN，附命令、环境、日志位置。
权限：本批次执行的外部动作及授权依据；没有则写“无外部写操作”。
动作：CONTINUE / CORRECT / HOLD。
下一步：继续哪一步、纠偏什么，或需要人类决定的具体问题。
```

检查点只展示可观察事实、决策理由和验证依据，不要求披露模型内部推理。原始输出和日志保存到受控证据目录；对人类或其他 Agent 展示时先按共享规则脱敏。不得在检查点、Issue、日志摘要或外发内容中回显凭据、Token、私钥或敏感数据。

### 6.5 经验和契约演进

- 每次任务结束后记录是否有可复用经验；只有得到授权的维护者可以更新账本。
- 经验只能按共享 review.md R13 的文件职责写入 review-experience.md 或仓库专属规则文件；不能写进产品实现、测试、普通 Issue 或 PR 作为隐性规则。
- Issue 契约版本采用递增版本，如 `v1`、`v2`、`v3`。初始发布为 `v1`。
- 修改 Theme、目标行为、允许/禁止范围、权限、依赖边界、验收预期或停止条件，必须升版本并取得新批准，固定新版本内容并记录改动摘要、原因和批准依据。
- 纯排版修正且不改变任何契约语义时可以不升版本，但必须保留更新记录；无法证明只是排版时按契约变化处理。
- 验收标准放宽、删减必需场景或把 FAIL 改成 N/A，必须由人类明确决定，记录原标准、新标准和理由，并升版本；Agent 不得自行放宽。
- 新版本发布后，旧验证结论不能自动迁移。分析者标记受影响的验收项；验证者确认前提未变的项目可以说明理由后复用，其余重新验证。
