## 11. Review 经验复利

### R13. 复盘、分层归属与更新

三个文件角色的职责见 §0.1。执行本节时，必须同时检索本轮选定的通用协议、`review-experience.md` 和 `review-[owner]-[repo].md`；不存在的文件如实记录，不自动创建。只查经验与仓库文件会漏掉已经上提的稳定规则。

每轮 Review 收尾时，必须复盘有效方法、误判、漏判、工具问题和执行踩坑，并回答：本轮问题本该由哪条规则或哪道门禁拦住；没有对应规则时，先记录案例，再判断是否够格新增规则。只把已经验证且后续可执行的结论写入对应文件，不保存完整事故流水或独立证据索引。

**新结论的归属判定**：

| 结论性质 | 写入位置 |
|---|---|
| 门禁、底线、跨项目强制判据 | `review.md`（需多项目或独立复现已证明） |
| 现象 → 判据 → 处理方式的诊断知识；环境/工具链基线 | `review-experience.md` |
| 仓库专属入口、命令、模块风险、数据布局、时效性基线 | `review-[owner]-[repo].md` |
| 尚未稳定、无法复用的一次性事故 | 不记录 |

同一根因只保留一个权威规范，不按 PR 或日期新增重复章节。经验上提为协议要求后，获授权维护经验文件时将对应处理要求改为规则 ID 引用；仍有价值的场景证据可以保留。无需为一次协议修订批量改写未授权的文件。

**时效性元数据**：`review-experience.md` 与仓库文件中的命令、版本、CI、分支、平台和工具链等时效性条目，必须在条目或所属章节中集中记录：

- `validated_at`：证据支持的最后实际验证日期；仅编辑、搬移或转述条目不更新该日期。
- `validated_ref`：验证时的 commit、tag、Base/Head 或其他固定引用。
- `applies_to`：适用分支、版本或范围。
- `toolchain`：仅在结论依赖工具版本时记录。
- `recheck_when`：workflow、manifest、依赖、分支、版本或相关入口发生何种变化时必须重新验证。

同一章节共享相同基线时只记录一次，不逐条重复。稳定的架构不变量、协议语义和仓库所有权边界无需机械添加时效元数据。

**规则写入例外**：在用户已授权维护经验规则的范围内，持久化规则写入只允许落到这三个角色对应的文件。证据目录中的报告与日志仍按 `R03` 保存。只有在本轮适用的扫描、验证、行内评论和执行对账完成后才能更新规则；任务明确指定只修改某一文件时，不据此扩大范围，也不得借此修改被审查仓库的源码、配置、测试或文档。

**引用纪律**：跨文件引用只用规则 ID 或章节号，永不用行号。修改本文件后，检查相关文件是否存在受影响的行号引用或已废弃措辞；在授权范围内改为 ID 引用，超出范围则报告具体位置与影响。

更新必须满足：

- 有本轮源码、Diff、命令输出或 GitHub 行为作为证据，不记录未经验证的猜测。
- 提炼为后续可执行的门禁、检查项、命令或失败处理方式。
- 新增规则使用下一个可用 ID 并登记进 §0.2 索引；不得复用或重排已有 ID。
- 不记录 Token、凭据、私有代码、用户数据、内部地址或其他敏感信息。
- 不得因为一次偶发现象制定过度宽泛的强制规则；必要时标明适用语言、平台或场景。
- 缺少时效元数据、超出 `applies_to` 或已经触发 `recheck_when` 的条目只能作为调查线索，必须基于当前 Base/Head 重新验证；不得凭该条目覆盖 `review.md`、归责 PR 或支持"可 Merge"结论。下次触及既有条目时补齐元数据，无需为本次规则调整批量扩写全部项目文件。
- 在收尾对账中列明本轮是否记录经验或更新协议；没有新增内容时写明"无新增可复用经验"。

**协议变更的回归验证**：修改本文件或经验文件中的判据、优先级或引用关系后，必须用已知的历史误判、漏判和撤回案例回归，确认新表述不会让既有案例漏检、改判或新增误报；回归不通过的修改不采用。尚无案例集时，至少复核受影响章节与相邻规则的交叉引用、`§0.4` 的冲突优先级与 `§0.2` 索引是否仍自洽，并在收尾对账中写明"未做案例回归"这一缺口。案例集只保存可复现的最小输入与预期结论，不保存完整事故流水。

收尾输出统一使用 §10 对账单中的"Review 经验复利"字段，本节不再重复定义第二份模板。
