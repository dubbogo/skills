## 8. 多轮审查与 Resolve

作者追加 commit 或用户要求复审时，先重新通过 `R02` 的状态门禁，再核对新 Head 的完整文件列表和 Diff 基准，审查增量、旧问题上下文及关联影响；不能因为此前审过就继续审查已转为 Draft、关闭或合并的 PR。force push 后重新取得新 Base/Head 的完整 Diff，不依赖旧提交顺序推断增量。历史证据保持其原 SHA；只有证明相关代码、依赖、配置和测试前提未变时才能引用为适用证据，否则重新验证。所有发布行号与合并状态按当前快照重新确认。

**same-tree Head 变更**：评论窗口内 `headRefOid` 变化时，即使新旧 commit 的 tree OID 与完整 Diff 相同，也要停止按旧快照收尾。核对 Base、父提交、tree OID 与 Diff，checkout exact 新 Head，重跑受影响的动态探针与门禁，再重新获取 comments/threads。只有 same-tree 已被 Git 对象证明且新 Head 复验结果一致时，才能复用源码推导；不得仅凭 commit message 或 Diff 文件大小判断等价。Head 前移期间创建的行内评论可能在响应或后续查询中被映射到新 Head，此时必须同时核对 `original_commit_id`、当前 `commit_id`、`position` 与 `isOutdated`。

自己或他人已发表的结论需要撤回或改判时，同样先取证再发声，不得只凭重新阅读代码就反转。撤回按证据类型区分：

- **确定性逻辑命题**：不依赖调度、外部 I/O、进程状态或真实锁竞争时，给出完整、可核对的执行轨迹、状态转换或反例即可支持撤回；不强制替换不存在的 I/O/锁边界。
- **依赖调度、I/O、子进程或锁生命周期的命题**：只有在满足 `R04` 的已核验隔离环境中，才允许在固定到 exact OID 的一次性副本里用可控桩或探针验证；记录替换边界、调度/触发条件、次数和结果。无隔离条件时不得执行探针，原结论维持为“尚未被反证”，并记录“无法反转”的验证缺口。
- **探针无法执行或未复现**：只能说明当前探针未得到反例，不得写成“该路径不存在”“不存在竞态”或“不会触发”；不得仅凭重复阅读或一次未复现撤回原判断。并发 Finding 的撤回必须针对原先给出的具体时序/触发条件证伪，而不是声称穷尽所有可能调度。

反转时保留原评论与历史证据，在原线程补充反证与新的定级，不删除、不静默改写。写入 `probes/` 的桩脚本和输出属于证据，执行前仍必须通过 `R04`。

仅当用户明确要求处理旧评论时才能 Resolve。原评论可以绑定旧 commit；Resolve 前必须通过线程身份（`R12` 的字段判据）和根因确认当前 Head 已完全修复该问题、验证证据充分且账号有权限。部分修复、当前 Head 仍可复现或证据不足时不得 Resolve，应在原线程说明残留问题。

**复审收敛与止损**：同一 PR 的复审必须有终止条件，不得用"再看一轮"替代判断。连续复审中重复出现的同一根因，先按 `§4` 核对是否属于本 PR 新增或扩大；属于基线的部分计入既有问题，不重复发布（`R12`）。若某一轮增量已无新增 P0/P1，剩余意见集中在首轮审查前即存在的旧代码，应停止逐行复审，改为按类一次性列出全部实例，并要求作者回到方案层重想方案。默认在第三轮复审后执行该判定，仓库文件可调整阈值但须给出理由。

**Head 不稳定止损**：一次审查中，Head 变化后允许按 `R02` 重取快照并重新开始受影响的审查；但连续两次重启审查后，Head 仍在完整取证或发布前再次变化，说明本轮无法建立稳定审查对象。停止继续发布评论和反复重启，向当前用户报告“Head 不稳定”，列出已观察到的 OID 与停止点；不得把未完成审查写成通过，也不得通过无限刷新快照空转。用户后续明确要求继续时，以新快照另开一轮。收尾时按 `§10` 记录复审轮次、本轮增量范围与未收敛原因；不得把"仍有意见"直接当作"审查未完成"的默认结论，也不得为凑轮次继续翻找基线问题。
