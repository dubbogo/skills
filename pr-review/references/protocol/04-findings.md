## 4. Finding 标准与优先级

每条 Finding 必须同时满足：

1. 能定位到本 PR 的 changed line，或明确说明无法行内定位。
2. 有可复现路径、源码推导、工具输出或规范依据。
3. 说明实际影响，而非个人偏好。
4. 给出可执行的修改方向；必要时指出应补的测试。
5. 排除 Base 已存在且本 PR 未扩大的问题。

**Finding 正文模板**：

```text
[P1] 简短标题
当前实现会在……场景导致……。证据是……。建议……，并补充……测试。
```

**量化要求**：以下类别不得只给定性描述——

- **性能类**：必须给出规模量级（n 是什么、实际或预期取值）与预期上界；主张"性能改善"时必须有测量或复杂度推导，不能只凭代码形态。
- **资源类**：必须说明哪个资源、在成功/失败/取消/超时/重启哪几条路径上未释放。
- **并发类**：必须给出可复现的调度或时序条件，不能只写"存在竞态"。
- **兼容性类**：必须给出受影响的既有输入样本或调用方，不能只写"可能不兼容"。

### [P0] 阻断级

有明确可达路径的严重安全或数据完整性破坏、大范围核心服务不可用等紧急问题，需要立即处理。说明触发条件、影响范围及为何达到紧急程度，不能仅凭"崩溃""泄漏"等问题类别定级。

### [P1] 必须修复

受支持的重要场景下导致显著错误、兼容性破坏、不可接受的资源消耗，或使适用的强制门禁失败，应在合入前修复。缺少测试只有在关键风险确实未获验证时才可能达到此级，不能仅凭"没有新增测试"定级。

### [P2] 建议修改

影响有限、可恢复且不阻断重要流程的真实缺陷，以及有明确收益的局部维护问题。说明具体影响或收益，不提交纯审美偏好。

严重性由影响范围、触发条件、可恢复性、支持平台和是否阻断核心流程决定，与复现把握度分开判断。真实 Bug 可以是 P2；测试失败需先区分测试缺陷、产品缺陷和环境问题，再判断等级。证据不足的猜测不通过提高等级形成 Finding。同根因的问题合并，避免重复评论。

### R14. 敏感信息与凭据处置

审查中发现疑似凭据、私钥或敏感数据时：

- 禁止在评论正文、报告或任何外发内容中回显敏感值，包括可能泄露信息的值前缀；使用文件、行号、类型和完全遮蔽的描述定位。先核对该值是实际凭据/敏感数据、失效值，还是占位符或合成测试数据。
- 有证据确认有效凭据已暴露时，应按泄露处理并告知责任人撤销或轮换；仅删除提交或改写历史不足以撤销访问能力。泄露不以当前代码读取该值为前提。核对来源、用途、权限与暴露范围，不用该凭据登录或调用服务验证有效性。
- 内部地址、其他敏感数据与凭据分别处理：核对真实敏感性、访问范围与泄露影响，确定删除、访问限制或其他处置方式；不能统一套用“轮换凭据”。占位符或合成测试数据不能仅因形似密钥就形成泄露 Finding。
- 按 §4 定级：只有明确证据支持紧急的严重安全或数据风险时定为 P0，其他已确认问题按影响定为 P1/P2。有效性或暴露范围尚不明时，向用户说明具体疑点、证据和缺口，不将推测写成已确认泄露。
- 发现于 Base 而非本 PR 时，仍必须告知用户，但不作为本 PR 的 Finding 定级；在收尾对账中单列。
- 未经用户明确授权，不得把仓库内容（含私有代码、配置、日志）发送给任何外部模型或服务用于复核。
