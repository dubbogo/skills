## 6. AI 生成或 AI 辅助 PR

### R07. 基本原则

**保留这类 PR，但不因"使用 AI"降低或提高标准。** 审查对象是变更风险、验证证据和维护责任，不是作者使用的工具。

不得仅凭文风、提交速度或代码风格猜测 PR 由 AI 生成，也不得以"AI 生成"为拒绝理由。作者无论是否使用 AI，都必须对代码、测试、许可证和后续维护负责。

### R08. 建议披露

项目可在 PR 模板中要求简短披露：

```text
AI assistance: none / code / tests / docs
Human verification: 已阅读全部 Diff，并执行 [commands]
```

不建议强制提交完整 Prompt、聊天记录或模型名称；这些信息难以验证，也可能包含隐私和机密。只有安全审计、许可证溯源或事故调查确有需要时再单独索取。

### R09. 加强检查信号

出现以下信号时提高审查深度，但仍须用代码证据形成 Finding：

- PR 过大或同时改动多个无关模块
- 描述与 Diff 不一致，作者无法解释关键设计
- 调用不存在、已废弃或语义错误的 API
- 重复实现已有能力或绕过项目抽象
- 大量看似完整但不可达的异常分支、兼容代码或注释
- 测试只复述实现、Mock 自身行为、缺少失败路径或关键断言
- 生成代码、依赖、许可证头或复制片段来源不明
- 安全、并发、协议、迁移或性能代码缺乏人工验证证据

加强措施：

1. 对任何来源的大而杂 PR，指出实质无关的变更及审查边界；必要时建议拆分，不因使用 AI 自动停止审查。
2. 对新增 API、依赖和配置查证官方文档或仓库实现；许可证与来源按 `R05` 的许可证门禁处理；复制片段必须给出上游 URL 与许可。
3. 人工推导至少一条正常路径、一条失败路径和一个边界场景。
4. 按 `R06A` 为关键回归核对反证，选择已有失败证据、Base/Head 对照或针对性变异，不机械全部执行。
5. 对许可证、来源、安全敏感代码和生成文件额外溯源。
6. 核心或高风险模块不得仅依赖 AI 审查，必须由人类维护者确认。

### R10. 不接受的做法

- 以"AI 已检查""模型说没问题"作为验证证据。
- 作者未读 Diff、无法解释核心逻辑或不承担维护责任。
- 用大量生成测试制造覆盖率，但未验证测试能发现错误。
- 把私有代码、凭据、用户数据或安全细节发送给未批准的外部模型。
- 自动生成、自动批准、自动合并形成无人负责的闭环。

AI 可以辅助生成、归纳和初筛，但最终 Merge 责任必须由有权限的人类维护者承担。
