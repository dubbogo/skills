## 10. 统计口径与汇报纪律

“纯 Rust 覆盖率”必须给出分母。默认按**本次验证输入集**统计，而不是宣称占全部业务行为或源码的比例：

- `N`：本输入集的有效执行 case；重复输入、生成失败、捕获不到的调用另列。
- `R`：完全由 Rust 处理的 case。
- `F`：完全或部分回退到原 Python 算法的 case；混合执行也计入回退。
- `E`：失败或无法确定实际执行路径的 case。
- 要求 `N = R + F + E`。报告 `R/N`、`F/N` 和 `E/N`；`N=0` 或未观测时写 `N/A`，不填 0%。

这衡量的是处理路径，不是行为一致率。另报一致、mismatch 和未比较数量；Python 适配层仍在运行也不等于算法发生回退。完整 Rust 应用还要单独验证原运行时依赖与完整产品入口。

返回契约要求的业务异常仍算该后端完成处理，不归入 `E`；已确认由 Rust 处理但输出错误的 case，在路径统计中计入 `R`，在行为统计中计入 mismatch。`E` 指执行失败或路径无法判定，避免把两个口径混在一起。

每条“通过”都有命令、退出码、摘要和完整日志路径；通常给出必要的输出行即可，不强制每次粘贴 10 行无关日志。不得编造性能倍数、覆盖百分比或全量测试结果。

禁止为通过而修改比较器、容差、skip、lint 或质量配置。允许有依据地修正测试缺陷、补充测试及必要构建配置；说明契约依据和影响，不能把合理开发工作一概封死。

参考实现出现明显缺陷时，记录并提出单独修复或明确的行为变更方案，不悄悄把修复混进等价移植，也不把已知错误包装成正确需求。

发现问题时给出位置、具体触发输入或时序、实际影响、证据和最小修正方向；同根因合并，不把个人偏好或工具告警直接当作缺陷。性能问题给出规模和上界，资源问题说明泄漏路径，并发问题给出调度条件，兼容问题指出受影响输入或调用方。分别判断本次引入/扩大、Base 既有、测试设施问题与环境问题。

交付结论分别说明：方向是否符合契约、代码是否有未修复缺陷、验收证据是否齐全、是否已接入默认入口。若另有已授权的 PR/发布任务，再报告 CI、审批、合并或发布状态；“单元验证通过”不自动等于可合并或已发布。未完成范围与已确认缺陷可以同时存在，不能用“没发现问题”掩盖未审范围。
