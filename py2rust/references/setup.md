# Python 项目 Rust 优化/迁移执行提示词

## 0. 使用方式与任务参数

这份提示词用于分析和执行任意 Python 项目的 Rust 优化或迁移。提示词中的计划、路径和历史结论都是待核实的输入，不能覆盖当前用户指令与目标仓库规范。

开始前填写或从当前会话确定：

- 仓库：`{{REPO}}`，填写本次实际 checkout 路径并核对仓库身份。
- 阶段：`分析选型` / `单元试点` / `已批准计划的后续单元`。
- 目标模式：默认是**性能驱动的增量迁移**；只有用户明确要求时才采用**完整 Rust 应用**模式。
- 当前单元：`{{UNIT}}`；分析阶段可为空，实施阶段必须明确输入、输出和调用入口。
- 已批准范围：`{{APPROVED_SCOPE}}`，包括行为边界、验收条件和是否允许接入默认运行路径；Issue 驱动任务还需记录契约版本、固定获批内容位置和可检索的原批准依据，开工与恢复时核对当前正文。
- 动作权限：默认仅本地修改、验证和报告；提交、推送、创建/更新 Issue 或 PR、发布评论、合并与部署分别按用户已有授权执行。
- 验证组织：记录获批执行模式、批准依据，以及宿主实际支持的独立上下文、快照传递与反馈能力；使用 issue-harness 时按 §3.4 核对开工条件，不能因能力不足自行降级。
- 工具组合：`{{TOOL_SELECTION}}`，按本项目和单元风险分别记录主流程所有者、产码路线、行为验收工具和主计时器；出现重叠时记录裁决，不把参考资料中列出的工具全部设为必选。
- 任务产物目录：`{{TASK_DIR}}`，优先复用当前 Issue 已约定的独占目录；并行任务分别维护状态，根迁移索引由明确的协调者更新。

首次会话默认只分析、产出计划，不自动实施整库迁移。用户批准具体单元后，完成该单元的实现与验证。已有会话授权继续有效，不因重启会话或完成某一步就反复要求确认。

后续会话读取 §9 的交接文件，核对实际源码和产物，然后继续已授权工作；只有目标、行为、兼容性、服务边界或发布范围出现实质变化时才补充确认。

### 0.1 配套资料的引用范围

本提示词采用同目录 `issue-harness.md` §1.1、§二至§六中的授权分离、任务契约、可验收切片与检查点方法，以及 `review.md` §2.2、`R05`、`R06`、`R06A`、`R15`、`R16`、§4–§5、§9中的相关证据判据。跨文件引用使用规则 ID 或章节号，不使用易漂移的行号；具体迁移要求写在本文，执行不依赖恢复原对话。

这些引用不整体启用 GitHub PR review 流程，也不继承发布评论、创建 Issue、修改经验账本或其他外部动作权限。进入单独授权的正式 PR review 时，再按选定的审查协议执行；迁移过程中只核对与本单元相关的风险和证据。
