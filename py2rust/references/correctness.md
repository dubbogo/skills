## 3. 正确性与执行边界

### 3.1 双重验证，还必须证明调用了 Rust

- **行为验证**：相关现有 Python 测试和外部契约测试保持原断言强度，在明确启用 Rust 的路径上执行。
- **差分验证**：固定的 Python 参考实现产生录制结果，Rust 实现逐案回放，比较返回值、异常及单元承诺的副作用。
- **执行路径证明**：验证真实入口加载了本次构建的扩展，记录扩展路径、构建身份和后端选择；在测试进程中强制 Rust 后端，扩展不可用或不支持时明确失败。测试全绿但实际全走 Python，不构成迁移通过。

参考端固定为迁移前实现，不能在替换导入后误把 Rust 当成录制源。差分记录与项目测试互相补充，二者都不能穷尽所有输入。

允许新增迁移回归、后端路由、构建安装和兼容性测试；必要时调整装配以运行同一行为测试的 Python/Rust 两个后端。不得为迁就实现而删除、跳过或放宽既有断言。改动测试装配时说明原因并保留原行为覆盖。

迁移改动测试文件时附断言变更清单：新增、删除、修改的断言数量与位置；删除或弱化必须给出契约依据并记入 `DECISIONS.md`。验证者核对清单，不以“测试全绿”代替覆盖核查。

### 3.2 兼容性不是“返回的 JSON 看起来一样”

根据单元契约比较：返回类型、顺序、数值、偏移、异常类型与错误码、必要的错误文本，以及事务、取消、超时、幂等或资源释放行为。只要求任务相关的契约，不盲目冻结内部调用顺序。

持久化身份、内容哈希、投影版本、排序与缓存绑定必须单独核对。若输出变化需要重建索引或迁移数据，这属于明确的兼容性变更，不能作为等价迁移悄悄提交。

### 3.3 有界推进

失败后先定位并在当前单元内修正，保留失败证据；不能把一次环境错误等同于实现错误，也不能因失败就跳到下一个单元。若连续尝试没有进展、关键依赖不可替代或需要扩大契约范围，给出证据、剩余差异和可选方案，再请求必要决策。

普通编译、调试、环境修复的尝试次数不等于正式检查点的 `CORRECT` 轮次。使用 issue-harness 的任务按其 §6.3 执行：同一验收项连续两轮正式 `CORRECT` 后仍失败，进入 `HOLD`，交人类决定恢复方式；获批契约若明确采用其他纠偏策略，记录依据并按该策略执行。不得把任意两条失败命令当成必须停工的条件，也不得无限纠偏或降低标准。授权范围内的普通可逆修复应自主完成。

### 3.4 检查点与独立验证

对实施单元设置开工、首个可验证切片和最终交付检查点；小单元可合并过程检查，关键接口或范围变化时补查受影响项。不要求逐行审批或固定频率轮询。

使用 issue-harness 时，执行模式与开工条件按其 §6.2：持续双 Agent 模式取得验证者对实际开工快照的 `CONTINUE` 后实施；`FINAL_INDEPENDENT_REVIEW` 或 `SELF_CHECK_ONLY` 需有针对适用契约和模式的人类批准依据。默认模式缺少必要能力或反馈时记 `BLOCKED / HOLD`，不能只改为“自检”标签后继续依赖该放行的步骤。已有明确的模式批准继续有效，无需重复确认；未采用该 harness 的本地任务按用户已授权范围和明确验收要求执行。

- coding agent 提交契约版本、代码快照标识、实际 diff 与新增文件、验证命令及原始输出位置，不能只提交自己的完成总结。
- 验证 agent 独立读取契约、原需求、源码和实际产物，检查目标、修改权限、实现与测试证据。默认只读被审文件；诊断探针在隔离副本运行，不修改被审实现、断言或验收标准。
- 方向与正确性分开报告：方向为“符合 / 偏离 / 证据不足”，验证为 `PASS / FAIL / BLOCKED / NOT_RUN`，动作反馈为 `CONTINUE / CORRECT / HOLD`。实现缺陷不自动等于偏离目标；目标相符也不代表测试通过。
- `CONTINUE` 仅放行当前阶段，不能代替全部验收或合并授权；`CORRECT` 在契约内修复后复查；`HOLD` 暂停受影响步骤并说明恢复条件，其余独立且已授权工作可继续。
- 等待实际验证反馈后再继续依赖该结论的步骤；受验快照保持可复现。修复后不能把旧快照结论直接套用到新产物。
- 人类主要处理目标、范围和无法消解的契约冲突；契约内普通修复由执行与验证闭环，不把检查点变成反复人工确认。

宿主必须真实传递产物并收到反馈，才能称为“过程独立验证”。只在结尾核验时写“最终独立验证”，只有同一执行者检查时写“自检”。任务明确要求独立验证而能力缺失时，该项记 `BLOCKED`，不能擅自降级成已完成。可复用适用于同一快照的可信证据，不为证明独立而机械重跑全部检查。
