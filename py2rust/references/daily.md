## 附：可直接使用的短提示词

> 在 `{{REPO}}` 按当前仓库规范执行 Python 项目的 Rust 优化或迁移。目标模式为 `{{MODE}}`，本轮阶段为 `{{PHASE}}`，单元为 `{{UNIT}}`，已批准范围为 `{{APPROVED_SCOPE}}`。
> 为本单元写清人类概览、可观察行为、不变量、允许/禁止范围、依赖所有者与验收；已有授权仅限本地时，不自行创建 Issue、发布评论或推送。
> 先核实 Head、工作区、调用契约与相关测试；Issue 驱动任务核对当前正文、固定批准版本和原批准依据。分别固定主流程、产码路线、行为验收工具和主计时器；工具按当前项目、版本和风险选定，互相重叠时记录唯一主责，不把历史案例工具组合设为必选。区分工具环境与产品工具链，已有明确实施授权则继续。
> 按函数或批量计算边界划分迁移单元，并按目标项目职责确定 Rust 代码归属。保持既有断言强度，允许必要的新测试；必须证明同一行为测试实际调用了本次 Rust 构建，不能靠 Python 回退获得全绿。
> 固定 Python 参考实现，录制无损 golden，再做 Rust 差分；核查异常、Unicode、数值、状态、副作用与持久化身份。工具生成的通配、容差和忽略顺序不得自动接受，不保存完整环境或凭据。
> 按项目生态选择绑定和打包方式；异步编排优先留在合适的原边界，不因迁移自动新增进程。核对 GIL（若适用）、取消、构建打包、干净环境安装和回滚。
> 完成相关测试、差分、含桥接成本的 bench、获批主工具检查和适用项目门禁后，才标记单元完成。报告实际命令与证据，按明确输入集分别给一致率及 Rust/回退/失败路径统计；未验证写未验证。
> 按获批执行模式设置检查点；使用 issue-harness 时核对对应开工放行，能力不足不可自行降级。获批模式要求独立验证时，让验证者读取实际快照和产物，分别判断方向与正确性；已有批准无需重复确认。关键验收验证检错能力，CI 核实际命令和选择集，结论绑定最终源码与二进制快照。
> 在任务独占目录更新 PORT-PLAN、DECISIONS、PORT-STATUS，共享索引由协调者维护。继续已授权事项；普通调试不按失败命令数停工，正式 CORRECT 轮次按获批策略和适用 harness 执行，不降低标准。
